# Нефункциональные требования

## 1. Назначение документа

Документ описывает нефункциональные требования к сервису планирования путешествий.

---

## 2. Производительность

| ID | Требование |
|---|---|
| NFR-001 | Система должна отвечать на стандартные запросы пользователя в пределах согласованного времени отклика для 95% случаев. |
| NFR-002 | Система должна выдерживать пиковую нагрузку на уведомления о задержках рейсов без потери критичных событий. |
| NFR-003 | Система должна поддерживать асинхронную обработку внешних событий, если синхронный ответ недоступен. |

---

## 3. Доступность и надёжность

| ID | Требование |
|---|---|
| NFR-004 | Система должна сохранять работоспособность при временной недоступности одного из внешних API. |
| NFR-005 | Система должна повторять запросы к внешним сервисам по согласованной политике retry. |
| NFR-006 | Система должна не терять пользовательские изменения при офлайн-режиме. |
| NFR-007 | Система должна поддерживать восстановление после сбоя без потери целостности поездки. |

---

## 4. Безопасность

| ID | Требование |
|---|---|
| NFR-008 | Паспортные данные должны храниться только в течение срока, необходимого для поездки и связанных проверок. |
| NFR-009 | Система должна ограничивать доступ к паспортным данным по ролям и контексту операции. |
| NFR-010 | Персональные данные должны передаваться по защищённым каналам связи. |
| NFR-011 | Система не должна хранить секреты доступа к внешним API в открытом виде. |

---

## 5. Работа со временем

| ID | Требование |
|---|---|
| NFR-012 | Все временные отметки должны храниться в UTC. |
| NFR-013 | Отображение времени пользователю должно учитывать его локальную временную зону. |
| NFR-014 | При расчётах пересадок и конфликтов система должна использовать явно заданные часовые зоны. |

---

## 6. Целостность и согласованность

| ID | Требование |
|---|---|
| NFR-015 | Система должна сохранять версионность плана поездки. |
| NFR-016 | При конфликте правок между участниками система должна явно сообщать о конфликте и не перезаписывать данные без проверки. |
| NFR-017 | Альтернативы должны формироваться на основании актуального состояния поездки и доступности внешних источников. |

---

## 7. Наблюдаемость

| ID | Требование |
|---|---|
| NFR-018 | Система должна логировать значимые события: создание поездки, изменение маршрута, уведомление, бронирование и синхронизацию. |
| NFR-019 | Система должна поддерживать корреляцию запросов и событий между внутренними и внешними компонентами. |
| NFR-020 | Ошибки внешних API и конфликты данных должны быть доступны для мониторинга. |

---

## 8. Хранение данных

| ID | Требование |
|---|---|
| NFR-021 | Система должна хранить только минимально необходимый набор паспортных и идентификационных данных. |
| NFR-022 | Система должна удалять или обезличивать чувствительные данные после завершения их использования. |
| NFR-023 | История изменений маршрута должна храниться в течение согласованного периода. |
